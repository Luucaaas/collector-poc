# P10-01 — README complet et guide du jury

## Brief

- **Objectif** : un lecteur du jury trouve en moins d'une minute, pour chacun des 10 critères de la grille, le livrable et sa preuve ; le `README.md` permet à quelqu'un qui ne connaît pas le projet de lancer le POC sur un cluster neuf en le suivant tel quel.
- **Contexte** : phase 10, critères 2 (« documenté », README exécutable) et 10, et tous les autres pour le guide. Grille : `Grille_eval_bloc_INFMAALSIA2V_Superviser_dev_apps_logicielles.xlsx` (racine du dépôt) et tableau « Ce que la grille exige » de `CLAUDE.md`. Avancement et livrables de chaque phase : section « Avancement » de `CLAUDE.md`. Le README actuel est daté par endroits (par exemple « Le lien vers les projets SonarCloud sera ajouté avec la tâche P5-04 »).
- **Fichiers concernés** : `README.md`, `docs/07-soutenance/` (créé : `README.md` d'index, `guide-jury.md`, `verifier-guide.py`), `docs/*/README.md` seulement si un index est faux, la fiche.
- **Contenu attendu** :
  - **`README.md`** réécrit pour un lecteur extérieur, en français, court en tête :
    - en quelques lignes, ce qu'est Collector.shop et ce que le POC démontre, avec le schéma d'architecture du POC (SVG existant) ;
    - lien vers le guide du jury en premier ;
    - badges de CI ; liens vers les projets SonarCloud (publics) ; aucune mention de tâches à venir ou de phases passées qui n'a plus de sens ;
    - **prérequis** (outils et versions, `deploy/local/check-tools.sh`, `mkcert -install` fait une fois par l'utilisateur, Docker Desktop avec ses ressources) ;
    - **démarrage sur le cluster** en commandes exactes (`cluster.sh create`, `deploy.sh all <tag>`, `smoke.sh`), avec le tag courant et la façon de trouver le dernier tag publié ;
    - **utiliser l'application** : adresses (`app.`, `api.`, `auth.`, `grafana.`), comptes de démonstration et leurs rôles, **emplacement** des mots de passe (clés de `deploy/local/.env`, jamais leur valeur), console d'administration de Keycloak par `kubectl port-forward` ;
    - pile `docker compose` (développement et tests d'acceptation), tests (pytest, acceptation, Vitest, Playwright, Locust) et leurs commandes ;
    - arrêt et nettoyage (`cluster.sh delete`, `down.sh`) ;
    - organisation du dépôt, à jour (`docs/06-securite`, `docs/07-soutenance`, `tests/load`, `frontend/e2e`…).
  - **`docs/07-soutenance/guide-jury.md`** : un tableau par critère de la grille (1 à 10) : ce que la grille demande pour 5/5 (formulation courte), où le trouver (liens relatifs vers les documents, scripts, résultats), les **preuves mesurées** (chiffres réels avec leur source : run de CI, fichier de résultats, rapport), et les limites assumées si elles comptent pour ce critère. Les chiffres viennent des documents du dépôt, jamais de mémoire : par exemple 17/17 critères d'acceptation, couverture, p95, HPA 2 → 5 en 60 s, pod remplacé en 4,9 s, 0 vulnérabilité HIGH corrigeable, 62 risques et 58 actions, plan de formation de 28 h. Plus une section courte « Parcours de lecture en 10 minutes ».
  - **`docs/07-soutenance/verifier-guide.py`** (bibliothèque standard) : vérifie que chaque lien relatif du guide et du `README.md` existe (et les ancres si possible), et que les chiffres cités se retrouvent dans leur fichier source quand c'est vérifiable simplement (liste explicite de couples chiffre → fichier). Sortie claire, code non nul en cas d'échec.
  - **Vérification du README depuis un cluster neuf** : suis le `README.md` **tel quel**, comme un nouvel arrivant : `deploy/local/cluster.sh delete`, puis les commandes du README (création, déploiement du tag courant `sha-1be69a1` ou du dernier tag publié sur `main` si plus récent, `smoke.sh`), puis `frontend/e2e/run-cluster.sh` (6 sur 6). Chaque écart entre le README et la réalité est corrigé dans le README (pas dans les scripts, sauf bogue à me signaler). Note la durée totale et les sorties résumées dans le journal.
- **Règles** : branche locale `phase-10/readme-guide` partie de `main`, non poussée ; jamais de commit sur `main`. Sur le cluster : seulement ce que le README fait faire (suppression et recréation du cluster comprises : il ne contient que des données de démonstration). Ne lance ni `mkcert -install` ni `-uninstall` ; aucune ressource Docker hors du projet ; aucun réglage de Docker Desktop. N'affiche jamais un mot de passe, un jeton ni le contenu d'un `.env`. Documentation et commits en français. Si un choix n'est pas prévu, arrête-toi et pose la question.
- **Hors périmètre** : script de démo (P10-02), support (P10-03), questions (P10-04) ; modification des documents de fond (signale une erreur trouvée, ne la corrige pas sauf dans un index).
- **Critères de fin** (vérifiables) :
  - [ ] `README.md` suivi tel quel depuis un cluster neuf : `smoke.sh` vert, Playwright 6 sur 6, aucun écart restant (durée et sorties dans le journal).
  - [ ] `guide-jury.md` : les 10 critères, chacun avec livrables, preuves chiffrées et sources.
  - [ ] `python3 -I docs/07-soutenance/verifier-guide.py` : 0 échec.
  - [ ] Aucune valeur de mot de passe ni chemin `/Users` dans les fichiers modifiés.
