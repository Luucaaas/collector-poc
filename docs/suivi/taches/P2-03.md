# P2-03 — Schéma CI/CD détaillé

## Brief

- **Objectif** : schématiser de façon détaillée le processus de livraison continue, du commit à la production (consigne 1.1.2, critère 4). Ce document est le **contrat** que le pipeline réel de la phase 5 devra suivre à l'identique : il doit être précis et réalisable.
- **Contexte** : phase 2 du plan. S'appuie sur la chaîne de CLAUDE.md (« Ruff + mypy → pytest + couverture → SonarCloud → build Docker multi-arch → Trivy → push GHCR »), sur `docs/01-qualite/indicateurs.md` (I1 à I5) et `docs/01-qualite/devsecops.md` (fusionnés), sur ENF-05, ENF-22, ENF-23, ENF-30 et la DoD de `docs/03-backlog/user-stories.md`. Décisions du chef déjà prises (voir `docs/suivi/journal-decisions.md`) : les tests d'acceptation tournent dans un job CI dédié sur une pile `docker compose`.
- **Fichiers concernés** :
  - `docs/01-qualite/cicd.md` (créé)
  - `docs/01-qualite/img/pipeline-cicd.svg` (généré par `docs/02-architecture/export-diagrams.sh`)
  - `docs/suivi/taches/P2-03.md` (journal uniquement)
- **Pipeline à décrire (décidé par le chef, ne pas changer)** — GitHub Actions, un workflow backend et un workflow front :
  - **Déclencheurs** : `push` sur toutes les branches et `pull_request` vers `main`. La publication sur GHCR n'a lieu que sur `main`.
  - **Backend**, en matrice sur `catalog-service` et `notification-service` :
    1. `lint` : `ruff check`, `ruff format --check`, `mypy --strict`. Bloquant.
    2. `test` : `pytest` (tests unitaires + tests d'intégration avec testcontainers PostgreSQL et RabbitMQ) avec `pytest-cov`, rapport `coverage.xml` et JUnit en artefact. Bloquant si un test échoue ou si la couverture < 80 % (`--cov-fail-under=80`).
    3. `sonar` : analyse SonarCloud avec le rapport de couverture, attente de la quality gate (`sonar.qualitygate.wait=true`). Bloquant si la quality gate échoue.
    4. `build-scan` : build de l'image amd64 chargée localement (Dockerfile multi-stage, non-root), scan Trivy de l'image (vulnérabilités OS et bibliothèques, secrets). Bloquant sur CRITICAL ou HIGH avec correctif disponible (`--severity CRITICAL,HIGH --ignore-unfixed --exit-code 1`). Rapport SARIF en artefact.
    5. `acceptance` (une seule fois, après `build-scan` des 2 services) : `docker compose up` (PostgreSQL, RabbitMQ, Keycloak avec le realm importé, les 2 images construites), attente des sondes `/health/ready`, puis `pytest tests/acceptance` (httpx). Bloquant. Rapport JUnit en artefact (alimente I5).
    6. `publish` (sur `main` uniquement, si tout le reste est vert) : build multi-arch amd64 + arm64 (Buildx, QEMU, cache) et push sur `ghcr.io/luucaaas/<service>` avec deux tags : `sha-<7 premiers caractères>` (propre au commit, jamais réécrit par la CI, utilisé pour le déploiement) et `main`. Seul le digest est immuable : le préciser.
  - **Front** (`frontend/`) : `npm ci` → ESLint → Vitest → `vite build` → image nginx non-root → Trivy (mêmes règles) → push GHCR `ghcr.io/luucaaas/frontend` sur `main`. Indiquer que ce workflow est mis en place en phase 7.
  - **Déploiement** (CD) : le cluster k3d est sur le Mac, inaccessible depuis GitHub. Le déploiement est lancé à la main par `deploy/local/deploy.sh <tag sha>` (`helm upgrade --install`), puis vérifié par `kubectl rollout status` et les sondes. Les consignes acceptent l'absence d'étape de déploiement automatique (le citer). Cible : Argo CD qui synchronise le cluster depuis Git (L12, ADR 0006).
  - **Après déploiement**, hors pipeline : tests de charge Locust (I3, phase 8), scan OWASP ZAP ponctuel (I4, phase 9), tableau de bord Grafana.
- **Contenu attendu de `cicd.md`** :
  1. Vue d'ensemble : environnements (poste du développeur avec `docker compose`, CI GitHub Actions, « production » = cluster k3d local), flux de branches (branche de tâche → fusion sur `main` après revue/audit → publication), déclencheurs.
  2. Le schéma Mermaid détaillé (`%% id: pipeline-cicd`) : jobs, enchaînements et dépendances (`needs`), conditions bloquantes (losanges ou libellés), artefacts produits, publication GHCR, déploiement manuel, étapes post-déploiement. Lisible à l'écran en soutenance : préférer `flowchart LR` découpé en sous-graphes (CI backend, CI front, CD, exploitation).
  3. Un tableau, une ligne par étape : job | outil et commande | condition de blocage | artefact | indicateur alimenté (I1 à I5) | mesure DevSecOps correspondante.
  4. Une section « Traçabilité » : de l'image déployée au commit (tag `sha-…`, digest, labels OCI `org.opencontainers.image.revision`).
  5. Une section « Écarts POC / cible » courte (Argo CD, environnement de recette, ZAP baseline et Gitleaks en CI : renvois L12, L13).
