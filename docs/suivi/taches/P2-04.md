# P2-04 — Processus de test

## Brief

- **Objectif** : formaliser le processus de test du projet (consigne 1.1.2, critère 7) : types de tests, outils, moment d'exécution, sortie attendue, responsables et parties prenantes.
- **Contexte** : phase 2 du plan. S'appuie sur `docs/01-qualite/indicateurs.md`, `docs/01-qualite/devsecops.md` et `docs/01-qualite/cicd.md` (fusionnés : le processus de test doit correspondre **exactement** aux jobs du schéma CI/CD), sur la stack de tests de CLAUDE.md (pytest, pytest-cov, testcontainers-python, tests d'acceptation pytest + httpx, Locust, Vitest, Playwright ; Trivy, SonarCloud ; OWASP ZAP ponctuel), sur la DoD et les 17 critères d'acceptation de `docs/03-backlog/user-stories.md`. Décisions du chef (journal des décisions) : tests d'acceptation dans un job CI sur pile `docker compose` ; Playwright lancé ponctuellement sur le cluster avant la démo, hors CI.
- **Fichiers concernés** :
  - `docs/01-qualite/processus-test.md` (créé)
  - `docs/01-qualite/img/pyramide-tests.svg` (généré par `docs/02-architecture/export-diagrams.sh`)
  - `docs/suivi/taches/P2-04.md` (journal uniquement)
- **Contenu attendu de `processus-test.md`** :
  1. Stratégie : pyramide des tests (schéma Mermaid `%% id: pyramide-tests`, simple et lisible), principes (tests écrits avec le code, aucun test fragile toléré, un test en échec bloque la fusion).
  2. Un tableau, une ligne par type de test : type | objectif | outil | emplacement dans le repo | moment d'exécution (poste, job CI, phase) | environnement et données | sortie attendue et critère de succès | responsable | indicateur alimenté. Types :
     - unitaires (pytest, logique métier : contrôle automatique, règles de prix, validation Pydantic, jetons expirés ou falsifiés) ;
     - intégration (pytest + testcontainers PostgreSQL et RabbitMQ : repository, publication et consommation d'événements, idempotence `ON CONFLICT DO NOTHING`) ;
     - API et sécurité de l'API (httpx sur l'application FastAPI : 401, 403, 422, propriété des ressources) ;
     - acceptation (`tests/acceptance`, pytest + httpx, un test par critère, nommage `test_usXX_caY_…`) ;
     - front : composants (Vitest) et bout en bout (Playwright, parcours de démo) ;
     - non-régression (définition : rejeu automatique de toute la suite à chaque push, plus un test ajouté pour chaque anomalie corrigée) ;
     - performance et charge (Locust, scénarios lecture du catalogue et publication, seuils ENF-12 et ENF-13) ;
     - disponibilité (suppression d'un pod et montée de l'HPA pendant Locust, ENF-16 et ENF-29) ;
     - sécurité (SonarCloud SAST, Trivy dépendances, image et secrets, OWASP ZAP ponctuel en phase 9).
  3. Traçabilité : critère d'acceptation → test d'acceptation → job CI → indicateur I5. Montrer un exemple sur US-03.
  4. Parties prenantes : tableau RACI (activités : écrire les tests, revoir les tests, exécuter la CI, valider l'acceptation, lancer la charge, analyser la sécurité) × rôles (Lead Developer, développeurs, Product Owner, direction Collector). Rester cohérent avec l'équipe du contexte (un lead dev, deux développeurs confirmés) ; un rôle QA ou DevOps n'apparaît que s'il est noté « recrutement envisagé (voir `docs/05-competences`) ».
  5. Gestion des anomalies : un test en échec → correction ou ticket, test de non-régression ajouté, données de test (comptes de démo du realm, fixtures).
  6. Lien avec la DoD de `user-stories.md` (ne pas la redéfinir, y renvoyer).
- **Hors périmètre** : écrire des tests ou de la configuration (phases 4 à 8). Nouveaux outils (pas de Gherkin/behave, pas de k6, pas de JMeter, pas de Postman/Newman, pas de mutation testing). Modifier les autres documents.
- **Critères de fin** (vérifiables) :
  - [ ] `docs/01-qualite/processus-test.md` existe avec les 6 sections et les 9 types de tests, chacun avec toutes les colonnes.
  - [ ] Chaque type exécuté en CI correspond à un job nommé dans `docs/01-qualite/cicd.md` (mêmes noms, même ordre), et aucun job de `cicd.md` exécutant des tests n'est oublié.
  - [ ] Les seuils cités sont ceux d'`indicateurs.md` et des ENF.
  - [ ] Aucun outil hors stack CLAUDE.md n'est présenté comme faisant partie du POC.
  - [ ] Le RACI n'utilise que des rôles du contexte ou des recrutements explicitement annoncés comme tels.
  - [ ] `docs/01-qualite/img/pyramide-tests.svg` généré par le script (sortie dans le journal), SVG de `docs/02-architecture/img` inchangés.
