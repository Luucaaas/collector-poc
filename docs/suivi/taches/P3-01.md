# P3-01 — Expérimentation 1 : RabbitMQ sur k3d

## Brief

- **Objectif** : prouver en bac à sable que RabbitMQ, installé sur un cluster k3d par l'opérateur officiel, transporte les événements du POC sans perte quand le consommateur ou le broker est supprimé en plein flux, et le documenter dans un protocole reproductible (critère 1, consigne 1.2.2).
- **Contexte** : phase 3 du plan. Décisions du chef (journal des décisions, 02/11/2026) : infrastructure installée par les **opérateurs officiels** (ici RabbitMQ Cluster Operator), pas de chart Bitnami ; un dossier par expérimentation dans `docs/04-experimentations/` ; code de bac à sable vérifié par Ruff et mypy, sans tests unitaires. Topologie et règles de fiabilité à reproduire à l'identique : `docs/02-architecture/contrats.md` l.155 à 170 (exchange `topic` durable `article.events`, file durable `notification.article-events` liée par `article.*`, messages persistants, confirmations de publication, acquittement après traitement, `prefetch = 10`). Limites connues : L2 (pas d'outbox) et L7 (pas de quorum queues ni de DLQ) de `architecture-poc.md`.
- **Fichiers concernés** :
  - `docs/04-experimentations/README.md` (réécrit : modèle commun des protocoles et index)
  - `docs/04-experimentations/01-rabbitmq/protocole.md` (créé)
  - `docs/04-experimentations/01-rabbitmq/run.sh` (créé, exécutable)
  - `docs/04-experimentations/01-rabbitmq/manifests/` (opérateur figé par version, `RabbitmqCluster`, Deployment du consommateur, Job du producteur)
  - `docs/04-experimentations/01-rabbitmq/app/` (projet uv : `pyproject.toml`, `uv.lock`, producteur et consommateur aio-pika, `Dockerfile` multi-stage non-root sur `python:3.12-slim`)
  - `docs/suivi/taches/P3-01.md` (journal uniquement)
- **Modèle commun des protocoles** (à écrire dans le README, puis à suivre) : 1. Objectif et question posée ; 2. Technologies testées et interactions (schéma Mermaid court si utile) ; 3. Environnement : machine, OS, Docker (CPU, mémoire), versions **exactes** de chaque outil, image et chart ; 4. Étapes reproductibles (`run.sh`, avec ce que fait chaque étape) ; 5. Décision (adoption, rejet ou conditions) et renvoi vers l'ADR.
- **Scénarios à exécuter réellement et à mesurer** :
  - A. Perte du consommateur : le producteur publie N = 1 000 messages numérotés (environ 50 par seconde, avec confirmations) ; le consommateur (Deployment, 1 réplica, traitement simulé de 20 ms, acquittement après traitement) est supprimé par `kubectl delete pod` au milieu du flux. Mesures : messages reçus distincts (attendu N), doublons (messages non acquittés relivrés), temps entre la suppression du pod et le premier message traité par le nouveau pod.
  - B. Perte du broker : pendant un flux, suppression du pod RabbitMQ (son volume persistant est conservé). Mesures : messages perdus (attendu 0 pour les messages confirmés), durée d'indisponibilité vue par le producteur et le consommateur, comportement de reconnexion (`connect_robust` d'aio-pika).
  - Méthode de comptage fiable même si un pod disparaît (les journaux d'un pod supprimé sont perdus) : par exemple, le consommateur publie un accusé (identifiant du message) dans une file durable `exp.receipts`, que `run.sh` vide et analyse à la fin. Une autre méthode est possible : la proposer au chef avant de l'utiliser.
- **`run.sh`** : crée le cluster `collector-exp1` (k3d, 1 server et 2 agents), installe l'opérateur et le `RabbitmqCluster` (1 nœud), construit l'image de l'app et l'importe (`k3d image import`), exécute A puis B, affiche un tableau de résultats, puis supprime le cluster (option `--keep` pour le garder). Idempotent, `set -euo pipefail`, versions figées en tête de script, aucun secret en clair dans le dépôt (identifiants générés par l'opérateur et lus dans son Secret).
- **Hors périmètre** : quorum queues, cluster RabbitMQ de 3 nœuds, DLQ, outbox (cible, L2 et L7 : les citer en limites). PostgreSQL, Keycloak, Traefik. Tests unitaires. Kafka.
