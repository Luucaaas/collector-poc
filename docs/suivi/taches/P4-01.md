# P4-01 — Socle de catalog-service

## Brief

- **Objectif** : construire la base technique de `catalog-service`, sans aucune fonctionnalité métier, et la couvrir par des tests. Le socle doit déjà appliquer les règles de sécurité et d'exploitation du POC : validation des JWT, contrôle des rôles, erreurs RFC 9457, logs JSON corrélés, sondes, métriques, arrêt propre et image non-root. Les tâches P4-02 et P4-03 ne feront qu'y ajouter des routes. P4-04 le recopiera pour `notification-service`.
- **Contexte** : phase 4 du plan, découpage validé par Lucas le 03/11/2026. Références obligatoires :
  - `docs/02-architecture/contrats.md` : §1.1 à §1.3 (exposition, authentification, formats, `X-Request-ID`) et §2.3 (endpoints techniques) ;
  - `docs/04-experimentations/README.md`, section « Synthèse et conséquences pour le POC », tableau de la phase 4 ;
  - `docs/04-experimentations/02-keycloak-tls/app/src/exp/app.py` : validation JWT de l'expérimentation, à reprendre en corrigeant les points de la synthèse ;
  - `docs/04-experimentations/03-observabilite/` : bornes d'histogramme ;
  - `docs/01-qualite/processus-test.md` (types de tests, couverture ≥ 80 %) et `docs/01-qualite/cicd.md` (jobs `lint` et `test` : commandes qui devront passer en CI) ;
  - décision du 31/10/2026 (journal) : en tests, les jetons sont signés par une clé RSA générée par la suite de tests, avec un JWKS de test, sans Keycloak.
- **Fichiers concernés** : `services/catalog-service/` (`pyproject.toml`, `uv.lock`, `src/catalog/`, `tests/`, `alembic.ini`, `migrations/`, `Dockerfile`, `.dockerignore`, `README.md`) et `docs/suivi/taches/P4-01.md` (journal uniquement).
- **Contenu attendu** :
  - **Projet** : Python 3.12, géré par uv ; paquet `catalog` dans `src/`. Versions exactes figées par `uv.lock`, en reprenant celles de l'expérimentation 2 quand elles existent : FastAPI 0.142.2, PyJWT 2.14.0, httpx 0.28.1, structlog 26.1.0, uvicorn 0.52.4. Ajouter Pydantic v2, pydantic-settings, SQLAlchemy 2.0, Alembic, psycopg 3 (un seul pilote, asynchrone pour l'application et synchrone pour Alembic) et prometheus-fastapi-instrumentator. Outils de développement : pytest, pytest-cov, testcontainers, Ruff et mypy.
  - **Application** : une fabrique `create_app()`. Configuration par variables d'environnement (pydantic-settings), dont l'URL de la base, `ISSUER`, `JWKS_URL`, `AUDIENCE` et l'origine CORS (`https://app.127.0.0.1.sslip.io`). Toutes les routes métier sont sous `/api/v1`.
  - **Authentification** (`contrats.md` §1.2) :
    - RS256 imposé avant et pendant `jwt.decode` ;
    - `iss` comparé à l'URL publique ; `aud = collector-api` ; `exp`, `iss`, `aud` et `sub` obligatoires ;
    - clés JWKS récupérées par l'URL interne, mises en cache (TTL), avec un rechargement limité sur `kid` inconnu ;
    - titre unique « Non authentifié » pour tous les 401, avec `WWW-Authenticate: Bearer` ; la raison du rejet reste dans les logs seulement ;
    - type de `realm_access` et de `roles` vérifié : un jeton signé mais mal formé donne 401, pas 500 ;
    - JWKS injoignable ou mal formé → 503 ;
    - dépendances réutilisables : utilisateur courant (`sub`, rôles) et rôle requis (403 « Accès refusé »).
  - **Erreurs** : format RFC 9457 (`application/problem+json`), avec `type`, `title`, `status`, `detail`, `errors[]` (`field`, `code`) et `correlation_id`, comme dans l'exemple de `contrats.md` §1.3. Gestionnaires pour la validation (422), les erreurs HTTP et les erreurs inattendues (500 sans détail interne). Modèle Pydantic de base avec `extra="forbid"`.
  - **Corrélation et logs** : `X-Request-ID` repris s'il fait au plus 128 caractères de `[A-Za-z0-9._-]`, sinon un UUID est généré. Il est renvoyé dans la réponse et écrit dans chaque log JSON (structlog) sous le nom `correlation_id`. Une ligne de log par requête (méthode, chemin, statut, durée). Aucun jeton ni secret dans les logs.
  - **Endpoints techniques**, non préfixés et non destinés à Traefik :
    - `/health/live` : sans dépendance ;
    - `/health/ready` : `SELECT 1` sur PostgreSQL, 503 si la base est injoignable, jamais RabbitMQ ;
    - `/metrics` : prometheus-fastapi-instrumentator, histogramme de durée avec des bornes qui encadrent les seuils d'I3 (300 et 500 ms), à justifier en citant le protocole 3.
  - **Base de données** : SQLAlchemy 2.0 asynchrone, une session par requête. Alembic configuré (URL lue dans l'environnement), avec une première migration vide qui sert de référence.
  - **Arrêt propre** : uvicorn lancé en forme `exec` dans l'image, qui reçoit SIGTERM. La durée d'arrêt de `docker stop` est mesurée et consignée dans le journal (attendu : bien moins que le délai de 10 s de Docker).
  - **Image** : Dockerfile multi-stage, base `python:3.12-slim`, utilisateur non-root, `uv sync --frozen`, sans outils de développement dans l'image finale. `.dockerignore`.
  - **README du service** : prérequis et commandes `uv sync`, `uv run ruff check`, `uv run ruff format --check`, `uv run mypy --strict src`, `uv run pytest --cov` et `docker build`, avec la liste des variables d'environnement.
- **Tests** (au fil de l'eau, aucune fonctionnalité sans test) :
  - **Unitaires** : validation du `X-Request-ID`, conversion des erreurs en RFC 9457, extraction des rôles.
  - **API et sécurité**, sur une route de test protégée ajoutée par les tests seulement, jamais dans l'application : jeton absent → 401, mauvais `iss`, mauvaise `aud`, expiré, signature altérée, autre clé, `kid` inconnu, algorithme `none` ou HS256 → 401 avec le titre unique ; `realm_access` mal formé → 401 ; rôle manquant → 403 ; JWKS en échec → 503 ; corps avec un champ inconnu → 422 au format RFC 9457 ; `X-Request-ID` valide repris, et trop long ou invalide remplacé.
  - **Intégration** : `/health/ready` contre un PostgreSQL de testcontainers (200), puis base arrêtée ou URL invalide (503). La migration Alembic s'applique sur ce PostgreSQL.
  - **Couverture** : ≥ 80 % (`--cov-fail-under=80`).
- **Hors périmètre** : routes métier, modèles métier et RabbitMQ (P4-02 et P4-03) ; `notification-service` (P4-04) ; `docker compose` et tests d'acceptation (P4-05) ; GitHub Actions (phase 5).
- **Critères de fin** (vérifiables) :
  - [ ] Dans `services/catalog-service`, `uv run ruff check`, `uv run ruff format --check` et `uv run mypy --strict src` passent.
  - [ ] `uv run pytest --cov=catalog --cov-fail-under=80` passe, avec Docker démarré pour testcontainers. Le journal donne le nombre de tests et le pourcentage de couverture.
  - [ ] Chaque cas de sécurité listé ci-dessus a son test, nommé de façon explicite.
  - [ ] `docker build` réussit. `docker run` de l'image répond sur `/health/live`. L'utilisateur du processus n'est pas root (`docker run --rm <image> id -u` ≠ 0). La durée de `docker stop` est relevée.
  - [ ] Aucun secret dans le dépôt ; aucune clé RSA de test versionnée (générée à l'exécution des tests).
- **Branche** : `phase-4/socle-catalog`
