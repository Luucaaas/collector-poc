# P4-04 — notification-service (US-05)

## Brief

- **Objectif** : créer `notification-service`. Il porte les centres d'intérêt et les préférences des acheteurs (API REST), consomme les événements `article.published` et `article.price_changed` de RabbitMQ et produit les notifications des acheteurs intéressés (US-05). Il valide la communication asynchrone entre services (critère 2) et ferme la boucle métier (critère 3).
- **Contexte** : phase 4, sur main après P4-03 (commit 0af8352). Décision validée par Lucas : le socle est **recopié** depuis `catalog-service`, pas partagé, pour que chaque service se construise et se déploie seul. Références :
  - `docs/03-backlog/user-stories.md` : US-05, avec 4 critères d'acceptation ;
  - `docs/03-backlog/exigences.md` §3 : RM-08 et RM-09 ;
  - `docs/02-architecture/contrats.md` :
    - §1, conventions communes : jeton, 401 et 403, RFC 9457, `X-Request-ID`, pagination de `GET /me/notifications` ;
    - §2.2, routes `/me/*` ;
    - §2.3, endpoints techniques ;
    - §3.1 à §3.5, topologie, garanties, enveloppe et schémas des événements consommés ;
    - §4.2, tables `interests`, `preferences` et `notifications` ;
  - `docs/04-experimentations/01-rabbitmq/app/src/exp/consumer.py` et `protocole.md` : consommateur et règle d'échec mesurés (scénario C) ;
  - les décisions finales des fiches P4-01 à P4-03 : durcissements du socle à reprendre tels quels.
- **Fichiers concernés** :
  - `services/notification-service/` : nouveau projet, avec `pyproject.toml`, `uv.lock`, `src/notification/`, `tests/`, `alembic.ini`, `migrations/`, `Dockerfile`, `.dockerignore`, `.env.example` et `README.md` ;
  - `docs/suivi/taches/P4-04.md` : journal uniquement ;
  - `docs/02-architecture/contrats.md`, seulement si une précision s'impose, et après question au chef.
- **Contenu attendu** :
  - **Socle recopié** de `catalog-service`, avec les mêmes versions dans `uv.lock` : configuration, logs JSON (uvicorn compris), RFC 9457, `X-Request-ID` borné, authentification (RS256, cache JWKS avec délai minimal et clés gardées en cache, timeout de 2 s, toute erreur en 503, titre unique des 401), `require_role`, `/health/live`, `/health/ready` (PostgreSQL seul), `/metrics` aux bornes d'I3, SQLAlchemy asynchrone, Alembic, Dockerfile multi-stage non-root, `pythonpath = ["src"]`. Paquet `notification`. Le README dit d'où vient le socle, et que toute correction du socle se fait dans les deux services.
  - **Migration `0001`** : tables `interests` (clé `(user_id, category_id)`), `preferences` (`user_id`, booléens par défaut `true`) et `notifications`, conformes à §4.2. `notifications` porte la contrainte `UNIQUE (user_id, source_event_id)`, un index sur `(user_id, created_at DESC)`, un CHECK sur `type` (`NEW_ARTICLE` ou `PRICE_CHANGED`) et un contenu `jsonb`.
  - **Routes** (§2.2, toutes en rôle `buyer`, utilisateur pris dans le `sub` du jeton) :
    - `GET` et `PUT /api/v1/me/interests` : `PUT` remplace la liste entière ; identifiants dédoublonnés ; plus de 20 catégories → 422. Le format UUID est vérifié, pas l'existence de la catégorie (§2.2).
    - `GET` et `PUT /api/v1/me/preferences` : sans préférences enregistrées, les deux types sont actifs.
    - `GET /api/v1/me/notifications` : pagination `limit` et `offset` (§1.3), notifications de l'utilisateur seulement, de la plus récente à la plus ancienne. Contenu exploitable par le front : type, article, titre, prix ou ancien et nouveau prix, date.
  - **Consommateur** :
    - lancé dans le lifespan de l'application, dans le même processus, et arrêté proprement à l'arrêt ;
    - connexion `aio-pika` robuste, file durable `notification.article-events` liée à l'exchange `topic` durable `article.events` par `article.*`, tous deux déclarés par le consommateur ;
    - `prefetch = 10` ;
    - le service démarre et reste prêt même si RabbitMQ est absent, puis se connecte dès que le broker revient.
  - **Traitement d'un événement** :
    - validation de l'enveloppe et de `data` (schémas de §3.4 et §3.5) ;
    - calcul des destinataires en une requête (§4.2) : intérêts sur la catégorie, préférence du type concerné (vraie par défaut), vendeur exclu (RM-08) ;
    - insertion en une transaction avec `ON CONFLICT DO NOTHING` (RM-09) ;
    - acquittement après le commit ;
    - `correlation_id` de l'événement repris dans les logs.
  - **Règle d'échec** (§3.1) : un message qui échoue est remis en file une fois, puis rejeté sans remise et journalisé (`message_rejected` avec `event_id`). Un message invalide (JSON ou schéma) est rejeté sans remise dès la première fois et journalisé.
  - **Métriques métier** : `notifications_created_total{type}`, `events_consumed_total{event_type, outcome}`.
- **Tests** :
  - **Unitaires** : validation des événements, construction du contenu des notifications, règle de calcul des destinataires.
  - **API** : chaque critère d'acceptation d'US-05, nommé `test_us05_ca1_...` à `test_us05_ca4_...`, avec 4 tests au minimum. Les CA2 et CA3 sont vérifiés en injectant de vrais événements dans RabbitMQ (testcontainers) puis en lisant `GET /me/notifications`. Pour le CA2, le délai mesuré doit être inférieur à 2 s. Tests en plus :
    - 422 au-delà de 20 catégories ;
    - préférences par défaut ;
    - isolation entre deux acheteurs ;
    - pagination des notifications.
  - **Intégration** (PostgreSQL et `rabbitmq:4.3.5-management` par testcontainers) :
    - même événement livré deux fois → une seule notification ;
    - message empoisonné → traité 2 fois puis rejeté, sans bloquer les messages suivants ;
    - message invalide → rejeté sans remise ;
    - vendeur non notifié ;
    - préférence désactivée respectée ;
    - démarrage sans RabbitMQ, puis connexion quand le broker arrive, avec `/health/ready` à 200 pendant ce temps ;
    - migration montante puis descendante.
  - Couverture ≥ 80 %.
- **Hors périmètre** : la publication d'événements (P4-03) ; les appels HTTP vers `catalog-service`, interdits (ADR 0001) ; l'envoi d'emails ou de notifications poussées, qui relève de la cible ; `docker compose` (P4-05).

  - [ ] Aucun appel HTTP vers `catalog-service`. Aucun secret versionné.
