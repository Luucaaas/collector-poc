# P4-05 — Pile docker compose et 17 tests d'acceptation

## Brief

- **Objectif** : livrer la phase 4. Une commande lance localement toute la pile du POC avec `docker compose` :
  - PostgreSQL avec une base et un utilisateur par service ;
  - RabbitMQ ;
  - Keycloak avec le realm `collector` ;
  - les deux services.

  Une autre commande exécute les **17 tests d'acceptation**, un par critère d'acceptation du backlog, de bout en bout, et ils passent 17 sur 17. C'est le livrable du plan de la phase 4 : « les 5 user stories fonctionnent en local avec docker-compose, et les tests passent ». Il sert aussi de base au job `acceptance` de la CI (phase 5) et au README exécutable (critère 2).
- **Contexte** : phase 4, sur main après P4-04 (commit 99d660e). Références :
  - `docs/03-backlog/user-stories.md` : les 17 critères (US-01 : 3, US-02 : 3, US-03 : 4, US-04 : 3, US-05 : 4) ;
  - `docs/01-qualite/processus-test.md` (§ acceptation, nommage, traçabilité vers I5) et `docs/01-qualite/cicd.md` (job `acceptance`) : la pile doit pouvoir démarrer à partir d'images déjà construites ;
  - `docs/02-architecture/contrats.md` : tout le document ;
  - realm et clients de test de l'expérimentation 2 : `docs/04-experimentations/02-keycloak-tls/realm/collector-realm.json` et `run.sh`, pour les marqueurs de mots de passe et le rendu ;
  - décisions du journal :
    - D2 de P3-05 : mots de passe générés dans un `.env` local non versionné, modèle `.env.example` ;
    - jetons des tests d'acceptation par un client *Direct Access Grants*, dans la pile de test seulement ;
    - un utilisateur PostgreSQL par service, sans droit de superutilisateur ;
    - rendu JSON des journaux `aio_pika` à reprendre dans `catalog-service`, décision de P4-04.
- **Fichiers concernés** :
  - `deploy/compose/` : `compose.yaml`, `.env.example`, scripts `up.sh` et `down.sh`, script d'initialisation de PostgreSQL, `README.md` ;
  - `deploy/keycloak/collector-realm.json` : realm de base, **sans client de test**, réutilisé en phase 6 ;
  - `tests/acceptance/` : projet uv propre avec `pyproject.toml`, `uv.lock`, `conftest.py`, les tests et un `README.md` ;
  - `services/catalog-service/src/catalog/logging.py` et son test : reprise de `notification-service` ;
  - `README.md` à la racine : section « Lancer le POC en local » ;
  - `docs/suivi/taches/P4-05.md` : journal uniquement.
- **Pile `docker compose`** :
  - **PostgreSQL** : `postgres:18.4-alpine`, volume nommé, `pg_isready`. Un script d'initialisation crée les bases `catalog_db`, `notification_db` et `keycloak`, chacune avec son propriétaire sans droit de superutilisateur, et retire l'accès `PUBLIC`, comme dans l'expérimentation 2.
  - **RabbitMQ** : `rabbitmq:4.3.5-management`, avec une sonde `rabbitmq-diagnostics`. Un utilisateur par service (`catalog`, `notification`), avec des mots de passe générés. Les permissions sont limitées au vhost du POC : c'est une limite à noter si elles restent larges.
  - **Keycloak** : `quay.io/keycloak/keycloak:26.8.0` en `start --import-realm`, sur PostgreSQL.
    - `KC_HOSTNAME=http://localhost:8080` : `iss` vaut toujours `http://localhost:8080/realms/collector`, même quand les services récupèrent les clés JWKS par `http://keycloak:8080` (constat de l'expérimentation 2) ;
    - sondes sur le port de gestion 9000 en HTTP.
    - Le realm monté est rendu par `up.sh` à partir du realm de base de `deploy/keycloak/`, avec les mots de passe générés et le **client de test** `collector-tests` (*Direct Access Grants*, scope d'audience `collector-api`). Le client de test n'existe que dans la pile compose : c'est une limite déclarée (RFC 9700).
  - **Services** : `image: ${CATALOG_IMAGE:-collector/catalog-service:local}`, avec `build:` vers le Dockerfile du service, et de même pour `notification`. La CI chargera ses images par `docker load` et passera ces variables.
    - Migrations Alembic par un service ponctuel par base (`command: alembic upgrade head`, avec la même image). Les services en dépendent par `service_completed_successfully`.
    - Sondes `/health/ready` sans outil ajouté à l'image, par exemple `python -c` avec `urllib`.
    - `ISSUER`, `JWKS_URL`, `AUDIENCE`, `DATABASE_URL` et `RABBITMQ_URL` viennent du `.env`.
    - Ports publiés sur `127.0.0.1` seulement : `catalog` sur 8001, `notification` sur 8002, Keycloak sur 8080, management RabbitMQ sur 15672 et AMQP sur 5672 pour les tests.
  - **`up.sh`** :
    - crée `.env` s'il n'existe pas, avec des mots de passe générés par le module `secrets`, et ne l'écrase jamais ;
    - rend le realm dans un dossier ignoré par Git ;
    - lance `docker compose up -d --build --wait` avec un délai borné ;
    - affiche les URL.
    
    `down.sh` arrête la pile, et `--volumes` supprime aussi les données.
  - Aucun secret versionné. `.env` et le realm rendu sont ignorés par Git, à vérifier.
- **Tests d'acceptation** (`tests/acceptance`, pytest + httpx, plus aio-pika pour observer les événements) :
  - **Les 17 tests, un par critère**, nommés `test_usXX_caY_<description>`. `test_us03_ca2_article_avec_coordonnees_rejete` est imposé par `processus-test.md`. Chaque test vérifie **tout** son critère, de bout en bout, sur la pile lancée :
    - pour US-03 CA1, US-03 CA2 et US-04 CA1, l'événement est observé (ou son absence vérifiée) par une file temporaire liée à `article.events` ;
    - pour US-05 CA2, la notification arrive par la vraie chaîne catalogue → RabbitMQ → notification, avec un délai mesuré sous 2 s.
  - **Jetons** : `admin`, `alice`, `bob` et `chloe` obtenus auprès de Keycloak par le client de test, avec les mots de passe lus dans `.env`.
  - **Rejouables** : noms et catégories uniques par exécution (suffixe aléatoire), aucune dépendance à l'ordre ni à un état préexistant. Deux exécutions de suite passent.
  - **Configuration** : URL de base et chemin du `.env` par variables d'environnement, valeurs par défaut sur la pile locale.
  - **Rapport** : JUnit XML (`--junitxml`) pour la CI.
  - Ruff, `ruff format --check` et `mypy --strict` passent sur `tests/acceptance`.
- **Reprise du socle** : `catalog-service/src/catalog/logging.py` rend aussi `aio_pika` et `aiormq` en JSON, comme `notification-service`, avec un test. La différence correspondante est retirée du README de `notification-service`.
- **README racine** : « Lancer le POC en local », avec les prérequis (Docker Desktop, uv) et les commandes `up.sh`, tests d'acceptation et `down.sh`. Il donne les URL, les comptes de démo (mots de passe dans `deploy/compose/.env`) et un exemple `curl` pour obtenir un jeton et appeler l'API.
- **Hors périmètre** : workflow GitHub Actions (phase 5), Kubernetes, Helm, Traefik et TLS (phase 6), front (phase 7), tests de charge (phase 8).
- **Critères de fin** (vérifiables) :
  - [ ] Depuis un état vide (`down.sh --volumes`), `deploy/compose/up.sh` lance la pile, et toutes les sondes sont saines dans le délai.
  - [ ] Les tests d'acceptation passent **17 sur 17** : sortie de pytest et nombre de tests dans le journal. Une seconde exécution de suite passe aussi.
  - [ ] Les noms des 17 tests correspondent aux critères, et `test_us03_ca2_article_avec_coordonnees_rejete` existe.
  - [ ] Les tests unitaires des deux services passent toujours, avec une couverture d'au moins 80 %, y compris après la reprise de `logging.py`.
  - [ ] Aucun secret ni mot de passe versionné (`git diff`, `.gitignore`). Le realm de base de `deploy/keycloak/` ne contient que des marqueurs et pas de client de test.
  - [ ] `down.sh --volumes` rend Docker propre : aucun conteneur ni volume de la pile ne reste. Les images construites peuvent rester.
- **Branche** : `phase-4/acceptance`
- **Agent** : developpeur
- **Fin de phase** : contre-vérification du chef. Il relance lui-même la pile et les 17 tests.
