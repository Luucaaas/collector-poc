# P5-02 — Jobs `build-scan` et `acceptance`, épinglage des images

## Brief

- **Objectif** : ajouter à `backend.yml` les jobs `build-scan` (matrice) et `acceptance` (une fois) du contrat, et épingler par digest toutes les images de base et d'infrastructure. Obtenir une exécution verte sur GitHub Actions, de `lint` à `acceptance`.
- **Contexte** : phase 5, critères 4 et 8. Contrat `docs/01-qualite/cicd.md`, lignes `build-scan` et `acceptance` de la section 3, et section 4 (traçabilité). Points reportés de la phase 4 : épinglage par digest, identifiants factices des tests face à Trivy, job `acceptance` avec `docker load`. La pile `deploy/compose/` (`up.sh --no-build`, `CATALOG_IMAGE`, `NOTIFICATION_IMAGE`, `down.sh --volumes`) existe et passe 17/17 sur le Mac.
- **Fichiers concernés** : `.github/workflows/backend.yml`, `services/*/Dockerfile`, `deploy/compose/compose.yaml`, éventuellement `deploy/compose/up.sh` ou `render.py` s'ils ne tournent pas tels quels sur Ubuntu, `deploy/compose/README.md` si le comportement change. La fiche.
- **Contenu attendu** :
  - **`build-scan`** (matrice, `needs: test` pour l'instant ; P5-04 insérera `sonar` entre les deux) : build de l'image **amd64 seule, chargée localement** (`docker/build-push-action` avec `load: true`, `push: false`, ou `docker build`). Argument de build `GIT_SHA` et labels OCI `org.opencontainers.image.revision` (SHA complet) et `org.opencontainers.image.source` (URL du dépôt) posés dans les Dockerfile. Puis Trivy exactement comme le contrat : `trivy image --scanners vuln,secret --severity CRITICAL,HIGH --ignore-unfixed --exit-code 1`. Puis `docker save` et `actions/upload-artifact` de l'image (une archive par service).
  - **Trivy et la chaîne d'approvisionnement** : en mars 2026, `aquasecurity/trivy-action`, `aquasecurity/setup-trivy` et la version 0.69.4 du binaire ont été compromis. Vérifie l'état actuel (avis de sécurité GitHub d'Aqua Security) et choisis une méthode sûre : action épinglée par SHA d'une version saine et publiée depuis plus de deux semaines, ou binaire d'une version saine téléchargé depuis la release officielle **avec vérification de la somme SHA-256**. Explique ton choix et sa justification dans le journal (le chef le reprendra dans le plan de remédiation).
  - **`acceptance`** (une seule exécution, `needs: build-scan`, ce qui attend les deux entrées de la matrice) : `actions/download-artifact`, `docker load` des deux images, lint du code de `tests/acceptance` (`ruff check`, `ruff format --check`, `mypy --strict .`, voir la décision du chef ci-dessous), `deploy/compose/up.sh --no-build` avec `CATALOG_IMAGE` et `NOTIFICATION_IMAGE` pointant vers les images chargées, `pytest` dans `tests/acceptance` avec `--junitxml`, upload du JUnit (`if: always()`), journaux des conteneurs affichés en cas d'échec (`docker compose logs`, `if: failure()`), puis `down.sh --volumes` (`if: always()`).
  - **Épinglage par digest** : `python:3.12-slim` dans les deux Dockerfile, et `postgres:18.4-alpine`, `rabbitmq:4.3.5-management`, `quay.io/keycloak/keycloak:26.8.0` dans `compose.yaml`, sous la forme `image:tag@sha256:<digest de l'index multi-architecture>` (le tag reste lisible, le digest fait foi ; l'index garde le fonctionnement sur le Mac arm64 et l'exécuteur amd64). Digest relevé avec `docker buildx imagetools inspect <image:tag>` ; commande et date de relevé notées dans le journal. Vérifier que la pile passe toujours 17/17 sur le Mac après l'épinglage.
  - Mêmes conventions que P5-01 (voir sa décision finale) : actions épinglées par SHA complet avec la version en commentaire, `runs-on: ubuntu-24.04`, `persist-credentials: false` sur `actions/checkout`, `if-no-files-found: error` sur les artefacts. Permissions minimales (`contents: read`).
- **Pousser la branche** : la branche est poussée sur `origin` (exception de la phase 5, voir P5-01). Ne jamais pousser sur `main`.
- **Décision du chef sur le lint de `tests/acceptance`** : la matrice `lint` porte sur les services ; le contrôle de `tests/acceptance` (`mypy --strict .`, Ruff) se fait dans le job `acceptance`, avant le démarrage de la pile. Le chef alignera la ligne `lint` de `cicd.md` en P5-05.
- **Hors périmètre** : `sonar` (P5-04), `publish` (P5-03), `cicd.md` et les schémas (P5-05, signale tout écart au chef), le chart Helm et le cluster (phase 6).
- **Critères de fin** (vérifiables) :
  - [ ] Une exécution GitHub Actions **verte** sur la branche, de `lint` à `acceptance` (2 × `lint`, 2 × `test`, 2 × `build-scan`, 1 × `acceptance` avec 17 passed). URL et durée de chaque job dans le journal.
  - [ ] Le journal du job `build-scan` montre le tableau Trivy (0 CRITICAL ou HIGH corrigeable, 0 secret) pour chaque service ; résultat recopié dans la fiche. Si Trivy signale quelque chose, ne pas l'ignorer en silence : corriger (mise à jour de la base ou de la dépendance) ou rendre la question au chef.
  - [ ] Les artefacts du run contiennent les deux archives d'image et le JUnit d'acceptance.
  - [ ] `docker inspect` sur l'image construite montre les deux labels OCI (sortie dans le journal).
  - [ ] `grep -n "@sha256:" services/*/Dockerfile deploy/compose/compose.yaml` montre les 4 images épinglées ; sur le Mac, `deploy/compose/down.sh --volumes && deploy/compose/up.sh` puis `cd tests/acceptance && uv run pytest` donne 17 passed, puis `down.sh --volumes`.
  - [ ] Preuve de blocage de Trivy : une exécution rouge provoquée volontairement par une **dépendance vulnérable** (par exemple une ancienne version d'une bibliothèque Python avec une CVE HIGH corrigée depuis, ajoutée dans un seul service sur un commit temporaire), URL notée, puis `git revert` et retour au vert. **Ne pousse aucun secret, même factice** : le dépôt est public et l'historique conserve tout.
  - [ ] Tests unitaires, `ruff check` et `mypy` des services toujours verts en local.
