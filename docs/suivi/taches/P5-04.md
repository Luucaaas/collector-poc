# P5-04 — Job `sonar` : SonarCloud, un projet par service

## Brief

- **Objectif** : ajouter le job `sonar` du contrat entre `test` et `build-scan`, avec un projet SonarCloud par service et l'attente du quality gate. Obtenir une exécution verte du pipeline complet.
- **Prérequis (Lucas, compte externe)** : les deux projets SonarCloud `Luucaaas_collector-poc_catalog-service` et `Luucaaas_collector-poc_notification-service` existent dans l'organisation `luucaaas`, l'analyse automatique est désactivée, et le secret GitHub `SONAR_TOKEN` est créé. Le chef vérifie ces prérequis avant de lancer la tâche (`gh secret list`, API publique `https://sonarcloud.io/api/components/search_projects?organization=luucaaas`). **Ne manipule jamais la valeur du jeton.**
- **Contexte** : phase 5, critères 4, 6 et 8. Contrat `docs/01-qualite/cicd.md`, ligne `sonar` : `sonar.projectKey` distinct, `coverage.xml` du job `test`, `sonar.qualitygate.wait=true`, blocage si le quality gate échoue. Décision du journal du 31/10/2026 (un projet par service). Point reporté de la phase 4 : identifiants factices des tests (mots de passe de test, jetons signés par une clé de test) à confirmer face à SonarCloud.
- **Fichiers concernés** : `.github/workflows/backend.yml`, `services/*/sonar-project.properties` (créés), la fiche.
- **Contenu attendu** :
  - Job `sonar` en matrice, `needs: test`, et `build-scan` qui passe à `needs: sonar`. `actions/checkout` avec `fetch-depth: 0` (SonarCloud a besoin de l'historique pour le code nouveau et le blame).
  - `actions/download-artifact` du `coverage.xml` du service ; chemins des sources corrigés si besoin pour que la couverture soit reconnue (vérifier que SonarCloud affiche la même couverture que pytest, à 1 point près).
  - Action officielle `SonarSource/sonarqube-scan-action` épinglée par SHA, `SONAR_TOKEN` en variable d'environnement depuis les secrets, `projectBaseDir` sur le dossier du service.
  - `sonar-project.properties` par service : `sonar.organization=luucaaas`, `sonar.projectKey`, `sonar.sources=src`, `sonar.tests=tests`, `sonar.python.version=3.12`, `sonar.python.coverage.reportPaths=coverage.xml`, `sonar.qualitygate.wait=true`.
  - Les problèmes signalés sur les identifiants factices des tests : ne pas les masquer globalement. Soit ils sont absents, soit tu proposes au chef une exclusion ciblée et justifiée (règle et fichiers précis). Ne marque rien comme faux positif dans l'interface SonarCloud.
- **Pousser la branche** : la branche est poussée sur `origin` (exception de la phase 5). Ne jamais pousser sur `main`.
- **Hors périmètre** : modifier les quality gates ou les réglages de l'organisation SonarCloud (compte de Lucas), corriger la dette de code relevée (le chef décide en P5-05 ce qui va au plan d'amélioration), `cicd.md`.
- **Critères de fin** (vérifiables) :
  - [ ] Run vert sur la branche avec, dans l'ordre, `lint` → `test` → `sonar` → `build-scan` → `acceptance`, et `publish` sauté (URL dans le journal).
  - [ ] Les deux projets SonarCloud ont une analyse de la branche ; pour chacun, relever dans la fiche : statut du quality gate, couverture, duplication, bugs, vulnérabilités, security hotspots, code smells, dette (API publique `api/measures/component` et `api/qualitygates/project_status`, commandes notées).
  - [ ] Preuve que le quality gate bloque, ou explication de pourquoi elle n'est pas démontrable sans modifier les réglages du compte (le chef tranchera).
