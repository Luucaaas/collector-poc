# P7-04 — Déploiement du front sur le cluster

## Brief

- **Objectif** : `deploy/local/deploy.sh services <tag>` (et `all <tag>`) déploie le front avec les deux services sur le cluster k3d, par le même chart Helm générique. `https://app.127.0.0.1.sslip.io` sert l'application en HTTPS avec ses en-têtes de sécurité, et la connexion au realm du cluster fonctionne (scope `profile`, redirection après déconnexion, page de connexion en français).
- **Contexte** : phase 7, critères 2 (hébergement, orchestration, sécurité), 5 et 10. Acquis :
  - image `ghcr.io/luucaaas/frontend:sha-<7>` publiée par `frontend.yml` (P7-03) à chaque push sur `main`, avec le même tag que les services ; tag de travail : celui du dernier run vert de `main`, donné par le chef dans le message de délégation ;
  - image nginx non root, uid 101, port 8080, sonde `/healthz`, modèles nginx traités par `envsubst` au démarrage (fiche P7-03) : avec `readOnlyRootFilesystem`, il faut des `emptyDir` sur `/tmp` et `/etc/nginx/conf.d` (modifiable par l'uid 101, d'où `fsGroup: 101`), et la variable `CSP_CONNECT_SRC` (origines de l'API et de Keycloak, séparées par des espaces) ;
  - le front lit `/config.json` au démarrage (`authority`, `clientId`, `catalogApiUrl`, `notificationApiUrl`) ; l'image contient déjà les valeurs du cluster, mais ce fichier doit venir d'un ConfigMap pour que la configuration se lise dans les values Helm (décision de la phase 7 : une même image partout) ;
  - chart `deploy/helm/collector-service/` (fiche P6-03) et `deploy/local/deploy.sh` (`check_images`, `services`, `rollback_all`, `smoke.sh`) ;
  - realm de base `deploy/keycloak/collector-realm.json` modifié en P7-01 (scope `profile`, `post.logout.redirect.uris`) mais **pas encore sur le cluster** : Keycloak (`start --import-realm`) n'importe pas un realm qui existe déjà. Sans cela, la connexion du front échoue (`invalid_scope`).
- **Fichiers concernés** : `deploy/helm/collector-service/` (templates et `values.yaml`), `deploy/helm/values/frontend.yaml` (créé), `deploy/local/deploy.sh`, `deploy/local/smoke.sh`, `deploy/keycloak/collector-realm.json` (français), `deploy/README.md`, `README.md` (section « Déployer sur le cluster local »), `docs/02-architecture/architecture-poc.md` (seulement si un fait décrit change), la fiche.
- **Contenu attendu** :
  - **Chart générique** (les deux services doivent produire **exactement** les mêmes manifestes qu'avant : compare `helm template` avant et après pour `catalog-service` et `notification-service`, sortie de `diff` vide ou expliquée ligne à ligne) :
    - chemins des sondes configurables (défaut : `/health/live` et `/health/ready`) ;
    - `secretName` facultatif (le front n'a pas de Secret) ;
    - uid, gid et `fsGroup` configurables (défaut 10001, front 101) ;
    - `emptyDir` supplémentaires configurables (le front : `/etc/nginx/conf.d`) en plus de `/tmp` ;
    - fichiers de configuration montés depuis un ConfigMap (le front : `config.json` dans `/usr/share/nginx/html/config.json`, en `subPath`, lecture seule), avec une annotation de somme de contrôle pour redémarrer les pods quand il change ;
    - Ingress : le mode « API » actuel (préfixe, `StripPrefix`, seul `<préfixe>/api/v1` routé) reste le défaut ; un mode « racine » pour le front (hôte `app.`, chemin `/`, sans `Middleware`) ;
    - migration et `ServiceMonitor` désactivables (le front n'a ni base ni `/metrics`) ; `deploy.sh` ne doit pas activer le `ServiceMonitor` du front ;
    - `CSP_CONNECT_SRC` passé par la section `config` (ConfigMap en variables d'environnement) : `https://api.127.0.0.1.sslip.io https://auth.127.0.0.1.sslip.io` ;
    - ressources du front adaptées à nginx (mesure la consommation réelle avec `kubectl top`, puis fixe des requests et limits raisonnables) ; HPA 2 à 5 comme les services.
  - **`deploy.sh`** : le front fait partie de `services <tag>` et `all <tag>` : `check_images` vérifie aussi `ghcr.io/luucaaas/frontend:<tag>` avant tout changement ; installation après les deux services ; `rollback_all` le couvre ; affichage des `imageID`. Le message d'usage et l'en-tête du script sont à jour.
  - **Realm du cluster** :
    - Page de connexion en français : `internationalizationEnabled`, `supportedLocales` `["fr"]` et `defaultLocale` `"fr"` dans le realm de base (la pile compose en hérite ; les parcours Playwright utilisent les identifiants `#username`, `#password` et `#kc-login`, à revérifier sur la pile compose : `frontend/e2e/run-compose.sh`, 6 sur 6).
    - **Mise à jour du realm sur un cluster existant** : le realm JSON reste la seule source de vérité. Cherche d'abord dans la documentation officielle de Keycloak 26.8 si `start --import-realm` peut écraser un realm existant (stratégie d'import). Sinon, ajoute une commande explicite `deploy.sh realm` qui applique le Secret `keycloak-realm`, recrée la base `keycloak` de PostgreSQL (seules les sessions sont perdues : comptes, rôles et clients viennent du JSON), puis redémarre Keycloak et attend la configuration OpenID. Cette commande ne s'exécute jamais toute seule depuis `all` ou `infra` sur un cluster existant ; documente-la dans `deploy/README.md`. Dans les deux cas, explique le choix dans la fiche. Si aucune des deux options n'est possible proprement, arrête-toi et pose la question.
    - Preuve : `https://auth.127.0.0.1.sslip.io/realms/collector/.well-known/openid-configuration` liste `profile` dans `scopes_supported` ; la page d'autorisation de `collector-web` avec `scope=openid profile` et `redirect_uri=https://app.127.0.0.1.sslip.io/` répond 200 avec un formulaire en français (vérifié par `curl`, sans soumettre de mot de passe).
  - **`smoke.sh`** (sans `-k`) : `https://app.127.0.0.1.sslip.io/` en 200 avec `Content-Security-Policy` (contenant les origines du cluster), `X-Content-Type-Options`, `Strict-Transport-Security` et `X-Frame-Options` ; `/config.json` en 200 avec `collector-web` ; une route de l'application (par exemple `/vendre`) en 200 (fallback SPA) ; `/.git/config` en 404. Les 8 contrôles actuels inchangés.
  - **Vérifications sur le cluster** :
    - `deploy.sh realm` (si créée), puis `deploy.sh services <tag>` sur le cluster en marche : 2 pods `Ready` par composant (3 composants), `smoke.sh` vert, `imageID` du front égal au digest publié par la CI ;
    - le pod du front : `readOnlyRootFilesystem`, uid 101, `kubectl exec … touch /usr/share/nginx/html/x` refusé ;
    - relance du même tag sans erreur ; tag inexistant refusé avant tout changement ;
    - un retour arrière du front : par exemple `DEPLOY_VALUES` avec une sonde qui échoue, `helm rollback` automatique, front revenu à la révision précédente (démarche du protocole 4, `docs/04-experimentations/04-deploiement/`) ;
    - mémoire : `kubectl top pods` du front et `docker stats --no-stream` des nœuds k3d, pour vérifier que l'ensemble tient dans les 8 Go.
- **Règles de la phase 7** (rappel) : branche locale `phase-7/deploiement-front` partie de `main`, non poussée ; jamais de commit sur `main` ; le cluster k3d `collector` est l'environnement de travail de cette tâche (tu peux y déployer, mais ne le supprime pas et ne lance pas `cluster.sh delete`) ; aucun conteneur, image ou volume Docker hors du projet ; aucun réglage de Docker Desktop ; ni `mkcert -install` ni `-uninstall` ; n'affiche jamais le contenu d'un `.env`, d'un Secret, d'un mot de passe ou d'un jeton (pas de `kubectl get secret -o yaml`) ; scripts bash `set -euo pipefail`, idempotents, commentés en français, compatibles avec le bash 3.2 de macOS, `shellcheck` sans erreur s'il est disponible ; code en anglais, documentation et commits en français. Si un choix n'est pas prévu, arrête-toi et pose la question.
- **Hors périmètre** : parcours Playwright sur le cluster et rapport de preuve (P7-05) ; `frontend.yml`, `backend.yml`, pages du front ; services backend ; observabilité du front (pas de `/metrics` côté nginx, limite acceptée pour le POC).
- **Critères de fin** (vérifiables) :
  - [ ] `helm lint` et `helm template` sans erreur pour les trois composants ; `diff` des manifestes des deux services avant et après : vide ou expliqué.
  - [ ] `deploy.sh services <tag>` : 3 composants à 2 pods `Ready`, `smoke.sh` vert (sortie dans le journal), `imageID` du front = digest publié.
  - [ ] Realm du cluster à jour : `profile` dans `scopes_supported`, page de connexion en français, procédure documentée et rejouable.
  - [ ] Sécurité du pod du front vérifiée (non root, lecture seule).
  - [ ] Retour arrière automatique du front démontré ; tag inexistant refusé.
  - [ ] `frontend/e2e/run-compose.sh` toujours à 6 sur 6 avec le realm en français.
