# P8-01 — Délai des notifications mesuré (ENF-14)

## Brief

- **Objectif** : `notification-service` expose une métrique Prometheus qui mesure le délai entre le fait métier (`occurred_at` de l'événement) et la disponibilité des notifications qu'il crée, pour vérifier l'exigence ENF-14 (p95 < 2 s) pendant les tests de charge de la phase 8, avec un panneau dans le tableau de bord Grafana.
- **Contexte** : phase 8, critère 6 (indicateurs réellement mesurés) et critère 3. ENF-14 dans `docs/03-backlog/exigences.md` (« p95 < 2 s entre l'horodatage de l'événement et la création de la notification », statut POC) : aujourd'hui rien ne le mesure. Références : `services/notification-service/src/notification/metrics.py` (`BusinessMetrics`, registre par application, bornes alignées sur les seuils comme pour I3), `consumer.py` (`process` : une transaction, un commit, compteurs incrémentés seulement après le commit), `events.py` (`occurred_at`, date-heure UTC), `docs/02-architecture/contrats.md` (§2.3 endpoints techniques et métriques, schéma des événements), tableau de bord `deploy/infra/monitoring/dashboards/collector-service.json`, `deploy/local/check-monitoring.sh`.
- **Fichiers concernés** : `services/notification-service/src/notification/metrics.py`, `consumer.py`, leurs tests, `deploy/infra/monitoring/dashboards/collector-service.json`, `docs/02-architecture/contrats.md` (liste des métriques), `docs/03-backlog/exigences.md` (seulement la colonne de mesure d'ENF-14 si elle doit nommer la métrique), `docs/01-qualite/indicateurs.md` (seulement si une ligne doit citer la métrique ; pas de relevé, c'est P8-04), la fiche.
- **Contenu attendu** :
  - **Métrique** : histogramme `notification_delay_seconds` (nom à garder tel quel, préfixe cohérent avec les autres si le projet en a un : vérifie), étiquette `event_type` (`article.published`, `article.price_changed`), bornes qui encadrent le seuil sans interpolation (par exemple `0.1, 0.25, 0.5, 1, 2, 5, 10`), docstring en français qui explique le choix des bornes comme le fait déjà `metrics.py`.
  - **Quand l'observer** : une fois par événement traité, **après le commit**, seulement si l'événement a créé au moins une notification (ENF-14 parle de la notification disponible ; un doublon redélivré qui ne crée rien, ou un événement sans acheteur intéressé, n'est pas compté). Valeur : instant après le commit moins `occurred_at`, en secondes. Un délai négatif (horloges décalées) est ramené à 0 et compté dans un compteur dédié ou signalé dans les logs (choisis le plus simple et justifie-le). L'horloge utilisée doit être injectable pour les tests (comme le reste du code, si un mécanisme existe déjà).
  - **Tests** (pytest, avec ceux qui existent) : observation après commit avec un délai connu ; pas d'observation si aucune notification n'est créée ; pas d'observation si la transaction échoue ; étiquette correcte pour les deux types ; délai négatif ramené à 0 ; la métrique apparaît sur `/metrics`. Couverture du service toujours au-dessus de 80 % (elle est à 98 %).
  - **Tableau de bord** : un panneau « Délai des notifications (p95) » (`histogram_quantile(0.95, …)` par `event_type`, sur une fenêtre cohérente avec les autres panneaux), avec le seuil de 2 s visible (ligne ou seuil coloré). Le panneau n'a de sens que pour `notification-service` : vérifie comment le tableau de bord gère le choix du service (variable) et dis ce que tu as fait.
  - **Documentation** : la métrique est ajoutée à la liste des métriques de `contrats.md` (et partout où les métriques de `notification-service` sont énumérées : cherche avec `grep`).
- **Livraison par la CI** : branche `phase-8/delai-notifications` **poussée sur origin** pour que `backend.yml` tourne (lint, test, build-scan, acceptance ; `sonar` et `publish` sautés sur une branche). Le chef fusionne, vérifie la publication sur `main`, puis déploie le nouveau tag sur le cluster et lit la métrique dans Prometheus. Ne déploie rien sur le cluster toi-même.
- **Règles** : jamais de push sur `main` ; aucune dépendance ajoutée (`prometheus_client` est déjà là) ; `ruff check`, `ruff format --check`, `mypy --strict src` et `pytest` passent ; code en anglais, docstrings, commentaires, documentation et commits en français ; aucun secret. Ne touche ni au cluster ni à Docker hors des testcontainers des tests. Si un choix n'est pas prévu, arrête-toi et pose la question.
