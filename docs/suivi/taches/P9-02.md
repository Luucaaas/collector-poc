# P9-02 — Corrections prioritaires du POC (dont L19)

## Brief

- **Objectif** : corriger dans le POC les 7 vrais positifs retenus de l'audit P9-01, déployer la version corrigée sur le cluster, et prouver par un nouveau passage de `docs/06-securite/scans/run-scans.sh` que chaque constat a disparu (avant et après), sans régression.
- **Contexte** : phase 9, critère 8 (« le POC intègre au moins deux bonnes pratiques pour sécuriser l'application » ; un plan dont une partie est déjà appliquée est plus crédible). Constats dans `docs/06-securite/rapport-scans.md` (section des propositions pour P9-02) et preuves dans `docs/06-securite/scans/resultats/20261110-1641/`. Décision finale de la fiche P9-01. Limite L19 de `docs/02-architecture/architecture-poc.md` §8.
- **Constats à corriger** :
  - **F-01** `zlib1g` (2 HIGH et 1 MEDIUM avec correctif Debian) dans les deux images de services : même méthode qu'en phase 5 (journal des décisions du 05/11/2026) : nouveau digest de `python:3.12-slim` qui contient le correctif, publié depuis au moins 14 jours si possible ; sinon dis-le et propose (question au chef) une autre voie.
  - **F-02** PyJWT 2.14.0 → 2.15.0 (2 MEDIUM) dans les deux services : `uv lock --upgrade-package pyjwt`, version exacte, date de publication dans le journal ; tous les tests d'authentification passent.
  - **F-03** `pip` présent dans l'image d'exécution (5 MEDIUM, 1 LOW) : le retirer de l'étage final (l'application n'en a pas besoin à l'exécution), sans casser le démarrage, les migrations Alembic (Job Helm) ni les sondes.
  - **F-06** (L19) console d'administration de Keycloak joignable sur l'hôte public `auth.` : l'Ingress de `auth.` ne route plus que les chemins publics nécessaires au navigateur et aux services (au minimum `/realms/` et `/resources/` ; vérifie ce que la page de connexion, la déconnexion et la configuration OpenID utilisent réellement) ; `/admin` répond 404 depuis l'extérieur ; la console reste accessible à l'administrateur par `kubectl port-forward` (commande documentée dans `deploy/README.md`). Les services joignent toujours Keycloak par l'URL interne (`JWKS_URL`), inchangée.
  - **F-07** en-têtes de sécurité absents : HSTS sur `api.` et `auth.`, `X-Content-Type-Options: nosniff` et en-tête CORP sur les réponses de l'API. Choisis le niveau le plus simple et cohérent (par exemple un `Middleware` Traefik `headers` posé par le chart sur l'Ingress de l'API et par le manifeste de Keycloak sur `auth.`, plutôt que du code dans chaque service), et justifie-le. Vérifie que CORS et la connexion du front ne sont pas cassés (la valeur de CORP doit être compatible avec un appel `fetch` depuis `https://app.127.0.0.1.sslip.io`).
  - **F-08** CSP du front `img-src 'self' https: data:` alors que le front n'affiche aucune image distante : resserrer (`img-src 'self' data:` ou ce que le front utilise réellement, vérifié dans le navigateur par le contrôle CSP des parcours Playwright).
  - **F-23** SonarCloud S9152 (`try/finally` autour du `yield` du `lifespan`) : corriger dans les deux services si la règle s'applique aux deux, sans changer le comportement d'arrêt (fermeture des connexions).
- **Preuves attendues** :
  - Tests : `ruff`, `ruff format --check`, `mypy --strict src`, `pytest` avec couverture ≥ 80 % dans les deux services ; tests ajoutés quand une correction touche le code (par exemple le lifespan) ; `npm run lint` et `npm test` si le front change.
  - `deploy/local/smoke.sh` : nouveaux contrôles (`https://auth.127.0.0.1.sslip.io/admin/` en 404, `/realms/collector/.well-known/openid-configuration` en 200, HSTS et `nosniff` présents sur une réponse de l'API).
  - Livraison : branche **poussée** (le code des services change) ; run `backend` et `frontend` verts sur la branche. Le chef fusionne, vérifie la publication, déploie le nouveau tag (`deploy.sh all <tag>` ou `infra` puis `services`, selon ce que tu as modifié : dis-le précisément) ; puis, à la demande du chef, tu relances sur le cluster `frontend/e2e/run-cluster.sh` (6 sur 6) et `docs/06-securite/scans/run-scans.sh` (nouveau dossier de résultats), et tu complètes `rapport-scans.md` d'une section « Après corrections » : pour chaque constat corrigé, preuve avant et après.
  - `architecture-poc.md` : L19 marquée traitée (ou réduite, si une partie reste : par exemple la confiance dans `X-Forwarded-*`), et une mesure de sécurité S ajoutée ou complétée pour les en-têtes ; `cicd.md` ou `conformite-pipeline.md` seulement si le digest de base y est cité.

Pas de déploiement sur le cluster avant la fusion (le chef s'en charge) ; ensuite seulement les exécutions demandées.
